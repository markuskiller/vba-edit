Overview

vba-edit is a set of command-line tools for Windows that move VBA code between an Office file and a folder of text files. There is one tool per application, and they all work the same way:

ToolApplicationTypical files
excel-vbaExcel.xlsm .xlsb .xls
word-vbaWord.docm
powerpoint-vbaPowerPoint.pptm
access-vbaAccess.accdb .mdb

Each tool has the same six commands:

CommandWhat it does
editExports the code, then watches the folder and copies every saved change into Office until you stop it.
exportWrites all modules to files, once.
importReads the files and updates the modules in the document, once.
checkTests whether Office lets programs reach the VBA project.
config-genOpens a window that builds a config file.
referencesLists, validates, exports and restores library references.

Every command explains itself with excel-vba <command> --help.

Beta software

vba-edit writes into your Office files. Keep a backup of anything important, keep the exported code in version control, and run export again after you change a form layout or module properties in Office.

Install

Requirements: Windows, and a desktop installation of the Office application you want to work with. The Python routes need Python 3.11 or later for 0.6.0; the stable 0.5.1 also runs on Python 3.10.

With uv installed, uvx runs a tool without installing it. This is the quickest way to try vba-edit.

PS> uvx excel-vba edit -f Budget.xlsm
PS> uvx word-vba export -f Letter.docm

The first run downloads the latest stable release. Later runs reuse that copy, so a new release does not arrive by itself: add @latest to fetch it, and ask for the version when in doubt.

PS> uvx excel-vba@latest --version    # fetch the newest release and show its number
PS> uvx excel-vba --version           # the copy that plain uvx runs

If you have installed a tool with uv tool install, uvx runs that installed version instead; uv tool upgrade updates it.

One package installs all four tools into your Python environment.

PS> pip install -U vba-edit

The optional xlwings wrapper for Excel needs xlwings as well: pip install -U "vba-edit[all]".

Standalone executables need no Python. Download them from the Assets section of the latest release: excel-vba.exe, word-vba.exe, powerpoint-vba.exe, access-vba.exe.

Open a terminal in the folder you saved them to and start them with a leading .\, because PowerShell does not run a program from the current folder otherwise. To call them from any folder, add that folder to your PATH and leave the .\ out.

PS> .\excel-vba.exe --version

The executables are not code-signed. Windows SmartScreen and some antivirus products warn about unsigned programs; the verification guide explains how to check the published SHA256 checksums and build attestations, and issue 24 has the background.

Installing the 0.6.0 pre-release

Features marked 0.6 in this guide are in the pre-release 0.6.0a4, not yet in the stable 0.5.1. Pre-releases are published to TestPyPI, with executables on GitHub. None of the routes above picks one up by itself; how you get it depends on how you run the tool.

Name the version, and TestPyPI as the first place to look:

PS> pip install -i https://test.pypi.org/simple/ --extra-index-url https://pypi.org/simple/ vba-edit==0.6.0a4

Into an environment managed by uv. One extra flag is needed because TestPyPI carries placeholder packages named like some dependencies:

PS> uv pip install vba-edit==0.6.0a4 --index https://test.pypi.org/simple/ --default-index https://pypi.org/simple/ --index-strategy unsafe-best-match

Without installing: name the package and its version with --from, and give both package indexes. The tool and its arguments come last.

PS> uvx --from vba-edit==0.6.0a4 --index https://test.pypi.org/simple/ --default-index https://pypi.org/simple/ --index-strategy unsafe-best-match excel-vba --version

Open the releases page and find the entry marked Pre-release; its Assets hold the four executables. The latest release link further up always leads to the stable version.

Whichever route you take, excel-vba --version should report 0.6.0a4 afterwards.

Allow VBA access

Excel, Word and PowerPoint refuse programmatic access to VBA code until you switch it on, once per application:

File›Options›Trust Center›Trust Center Settings…›Macro Settings›☑ Trust access to the VBA project object model

Access has no such checkbox. It needs the database to be trusted instead: keep it in a trusted location or enable its content when Access asks.

Without this, commands stop with Cannot access VBA project and point you to the Trust Center. The check command tests the setting for you.

check
PS C:\Projects\budget> excel-vba check

Editor setup

Any editor works. Two things are worth setting up: the file encoding and syntax highlighting.

The VBA editor is not Unicode-aware; it stores code in the Windows code page of your system, which is Windows-1252 on Western European and US systems. vba-edit writes files in that same encoding by default, so your editor should read and save them the same way. Otherwise umlauts, accents and symbols such as € get mangled on the way back.

For VS Code, add this to your user settings.json (and to each profile, if you use profiles). A VBA language extension provides the vba language mode.

"[vba]": {
    "files.encoding": "windows1252"
},
"files.associations": {
    "*.bas": "vba",
    "*.cls": "vba",
    "*.frm": "vba"
}

If your system uses another code page, or you pass a different --encoding, set the same one here.

Concepts

What ends up on disk

Each component of the VBA project becomes one file, named after the component:

In the VBA projectFileNotes
Standard moduleName.bas
Class moduleName.cls
UserFormName.frm + Name.frxThe .frx holds the binary layout. Needs a header option.
Document moduleName.clsThisWorkbook, sheet modules, ThisDocument, slide modules, and Access Form_… / Report_… code.

The sample workbook used throughout these docs exports like this:

export, then a look at the result
PS C:\Projects\budget> excel-vba export -f Budget.xlsm --vba-directory src
PS C:\Projects\budget> Get-ChildItem src -Name
PS C:\Projects\budget> Get-Content src\Reporting.bas

Depending on the options you use, a few more files can appear in the same folder:

Name.header
The module's header (version line, attributes), written by --save-headers.
vba_metadata.json
Written by --save-metadata, and automatically whenever UserForms are exported. It records the source document, the export date, the header mode and the encoding and type of each module. vba-edit uses it to notice when you switch header mode.
<document>_refs.toml
The project's library references, written by --with-references.
.vba-edit/
State and recovery snapshots of bidirectional editing. Keep it out of Git, but do not delete it between sessions.

Where the folder is. By default the files are written next to the document. --vba-directory DIR chooses another folder and creates it if needed; a relative path is taken from the directory you run the command in. The value may contain placeholders such as {file.name}.

Document modules in other languages. Office names these modules in its interface language: ThisWorkbook is DieseArbeitsmappe in German and CeClasseur in French, sheets are Tabelle1 or Feuil1. vba-edit recognises the common localized names, and otherwise goes by the module's header and by what already exists in the document.

Which document is used

Every command that works on a document accepts --file (short -f). Without it, the tool uses the document that is currently active in the application. With it, the tool opens the file if it is not open yet.

PS> excel-vba export                          # the active workbook
PS> excel-vba export -f Budget.xlsm           # this file

If nothing is open and no file is given, the command stops and asks for --file.

File types

The everyday formats are .xlsm, .xlsb, .xls for Excel, .docm for Word, .pptm for PowerPoint, and .accdb, .mdb for Access. Templates and add-ins (.xltm, .xlam, .dotm, .potm and so on) are recognised as belonging to their application and are likely to work, but have seen little testing.

Hand a file to the wrong tool, say a workbook to word-vba, and you get an extension mismatch message naming the tool to use instead.

What stays open afterwards

CommandDocument it opened itselfDocument that was already open
exportClosed again without saving; the application is closed too if vba-edit started it. --keep-open leaves both open.Left open, untouched 0.6
importSaved and left open.Saved and left open.
editLeft open; saved after each synced change.Left open; saved after each synced change.

In 0.5.1, export closed a document that was already open without saving it. Save before exporting if you are on the stable release.

Commands

edit

The command you will use most. It exports the code, then keeps running and copies each saved file into the document.

excel-vba edit [-f FILE] [--vba-directory DIR] [--save-headers | --in-file-headers] [--save-metadata] [--rubberduck-folders] [--include PATTERN …] [--exclude PATTERN …] [--encoding ENC | --detect-encoding] [--with-references] [--bidirectional [--sync-resolve {office,files} --sync-component NAME]] [--open-folder] [--force-overwrite] [--conf FILE] [--verbose] [--logfile [FILE]] [--no-color]
a complete edit session
PS C:\Projects\budget> excel-vba edit -f Budget.xlsm --vba-directory src

What happens, step by step

  1. Start. Modules that have no file yet are exported. Files that already exist are left as they are, and they are not pushed into Office at this point either. If your files are newer than the document, run import once before you start.
  2. Watch. The folder is watched for .bas, .cls and .frm files (including subfolders with --rubberduck-folders).
  3. Save. When you save a file, its module is updated in the document and the document is saved. A new file becomes a new module.
  4. Stop. Ctrl+C ends the session. The document stays open.

Three things to know

  • Deleting a file deletes the module in the VBA project. Document modules such as ThisWorkbook cannot be deleted and stay.
  • Changes typed into the VBA editor are not copied back to your files. Run export to fetch them, or use --bidirectional.
  • Closing the document ends the session. Edits you save afterwards are not lost, because they are in your files, but nothing applies them by itself: a new edit session leaves existing files alone (step 1). Run import once, then start edit again.

Editing a .header file on its own does not trigger a sync. Save the matching code file as well and the whole module is brought across.

Two options exist only on other commands: --skip-empty (export and import) and --keep-open (export).

export

Writes every module to a file, once. Use it for a first snapshot, before a commit, or to fetch changes that were made in the VBA editor.

excel-vba export [-f FILE] [--vba-directory DIR] [--save-headers | --in-file-headers] [--save-metadata] [--rubberduck-folders] [--include PATTERN …] [--exclude PATTERN …] [--encoding ENC | --detect-encoding] [--with-references] [--skip-empty] [--keep-open] [--open-folder] [--force-overwrite] [--conf FILE] [--verbose] [--logfile [FILE]] [--no-color]
--skip-empty
Leaves out modules without code. Handy for workbooks with dozens of empty sheet modules.
--keep-open
Keeps the document open after the export, for a look at the result. Without it, a document that vba-edit opened is closed again.
--open-folder
Opens the export folder in File Explorer when done.
--force-overwrite
Skips the confirmation prompts. Meant for scripts.
--save-metadata -m
Writes vba_metadata.json beside the code (see what ends up on disk).

If the folder already contains VBA files, export asks before it replaces them. See safety prompts for what that looks like.

Result and exit code

If a module cannot be exported, the others are still written. The run then ends with a message such as 1 of 5 VBA components could not be exported: Broken and a non-zero exit code, and an edit session does not start. Fix the cause, or leave the module out with --exclude.

Up to 0.6.0a4, such an export logs the error for the module and still ends with exit code 0, even if no module could be exported. Read its output before relying on the files. Reported with an exit code after 0.6.0a4.

import

Reads the files in the folder and updates the document, once. It is the counterpart to export and what you run after editing without a live session.

excel-vba import [-f FILE] [--vba-directory DIR] [--rubberduck-folders] [--include PATTERN …] [--exclude PATTERN …] [--encoding ENC | --detect-encoding] [--with-references] [--skip-empty] [--conf FILE] [--verbose] [--logfile [FILE]] [--no-color]

There are no header options here because none are needed. For each file, import looks for a header inside the file first, then for a separate .header file, and otherwise creates a minimal one.

What import does to each kind of module

ModuleHow it is updated
Standard moduleIts code is replaced in place; a new file creates a new module.
Class moduleCode is replaced in place when the header is unchanged. Only a changed header, or member attributes such as VB_UserMemId, cause the module to be removed and imported afresh. 0.6 A class that is new to the document is imported together with its header, whether that is in the file or in a .header file.
UserFormImported as a whole, with its .frx. A .frm without any header is refused, and the form in the document is left as it was. 0.6
Document moduleCode is replaced in place. These modules belong to the document and cannot be created by an import.

Modules that exist in the document but have no file are left alone: import never deletes anything.

If an update fails, the module is put back as it was. After a failed code replacement that is the previous code. A class module or UserForm that has to be replaced as a whole is copied first, a form together with its layout, and the copy is imported again when the new version cannot be. The file is then reported as failed, and the document still holds the original.

Up to 0.6.0a4 only code replacements are undone. There, a class module or UserForm whose re-import fails is missing from the document afterwards, and stays missing until an import of its file succeeds; your files still have it. Also up to 0.6.0a4, a class that is new to the document and has a separate .header file is created with default attributes, so VB_PredeclaredId and the like only arrive with a second import. Both are fixed after 0.6.0a4.

Result and exit code 0.6

The run ends with a summary such as Imported 4 of 5 VBA files; 1 failed: Broken.bas, and the exit code is non-zero when a file could not be imported. Scripts and coding agents can rely on that. The document is saved and left open.

To import only some files, add a module filter:

PS> excel-vba import -f Budget.xlsm --vba-directory src --include "Rep*" Helpers.bas

check

Tests whether the application lets vba-edit reach VBA projects, and tells you what to change if not.

PS> excel-vba check          # this application
PS> excel-vba check all      # Excel, Word, PowerPoint and Access

The check creates a scratch file in a temporary folder of its own, tries to read its VBA project, then closes the scratch file and removes the folder. It starts the application if needed and closes it again; an application you already had open stays open, with your documents untouched. If Access already has a database open, the check looks at that database's project and creates nothing.

Up to 0.6.0a4: empty folder, application closed

In 0.5.1 and the pre-releases up to 0.6.0a4, the scratch file is created in the current directory as test.xlsm, test.docm, test.pptm or test.accdb. A file of that name that is already there is overwritten or deleted, and the application is closed at the end even if you had it open. With those versions, run check from an empty folder and with the application closed. This is fixed after 0.6.0a4.

config-gen

Opens the Config Generator, a small window for building a config file without writing TOML by hand. It is part of the normal install.

PS> excel-vba config-gen
  • The General tab has the document and folder pickers, the header mode, the encoding, switches for the remaining options, and fields for include and exclude patterns.
  • The References tab has the references file and its filters.
  • The TOML Preview updates as you click. Open Config… loads an existing file into the form; Save Config… writes it.

Each tool opens the generator for its own application, so the file picker shows the right file types and Excel gets its extra xlwings switch.

references

A VBA project can reference external libraries, such as Microsoft Scripting Runtime, ActiveX Data Objects, or another document or add-in. The references live in the document, which makes them invisible in code review and easy to break when a file moves to another machine. This command makes them visible and portable.

Access needs a version after 0.6.0a4

In 0.6.0a4 the references commands and --with-references stop with a Reference error when used with access-vba. This is fixed after 0.6.0a4. Note that Access lists its database engine library (DAO) as INSTALLED, not as DEFAULT.

SubcommandWhat it does
references listShows every reference with name, version, GUID, path and description.
references exportWrites the references to a TOML file.
references import -r FILEAdds the references from a TOML file. Existing ones are skipped. With --sync, also removes references that are not in the file. Exits with code 1 if a reference could not be processed; the others are kept.
references validateReports broken references. Exits with code 1 if it finds any.
references add LIBRARYAdds one reference by file path (.xlam, .dotm, .dll, .olb, …).
references remove NAMERemoves one reference by the name shown in list.

All of them take -f FILE like the other commands. A document that is already open is used as it is and stays open. export and import take -r FILE (--refs-file) for the TOML file; the default is <document>_refs.toml next to the document.

In 0.6.0a4, close the document first

Up to 0.6.0a4, a references command with -f closes the document afterwards without saving, even if you had it open with unsaved changes. Save or close the document before you run one. This is fixed after 0.6.0a4.

references: list, filter, export, validate
PS C:\Projects\budget> excel-vba references list -f Budget.xlsm
PS C:\Projects\budget> excel-vba references list -f Budget.xlsm --no-default
PS C:\Projects\budget> excel-vba references export -f Budget.xlsm -r budget-refs.toml --no-default
PS C:\Projects\budget> excel-vba references validate -f Budget.xlsm

Three kinds of reference

KindMeaningExamplesHide with
DEFAULTPresent in every new document.VBA, the host application, stdole, Office--no-default
INSTALLEDA library registered on the system, identified by its GUID.Scripting Runtime, ADO--no-installed
CUSTOMA reference to a file, identified by its path.your own .dotm or .xlam--no-custom

The three filters work on list and export and can be combined.

The TOML file

The exported file is plain TOML that you can read, diff and edit. A [metadata] table records how it was produced, and each reference is one [[references]] entry:

# a registered library, found by GUID on any machine
[[references]]
name = "Scripting"
guid = "{420B2830-E718-11CF-893D-00A0C9054228}"
major = 1
minor = 0
description = "Microsoft Scripting Runtime"

# a file reference, found by path
[[references]]
name = "SharedMacros"
path = '\\server\share\templates\SharedMacros.dotm'
major = 0
minor = 0

Sync: make the document match the file

A plain references import only adds. With --sync, references that are not in the file are removed as well.

PS> excel-vba references import -r shared-refs.toml --sync

Two protections apply unless you add --force-overwrite: default references are never removed, and a file that was exported with filters is refused, because syncing from it would remove exactly the references you chose to leave out.

References alongside the code

--with-references on export, import and edit handles the references in the same run. The file is always named <document>_refs.toml and lives in the VBA folder.

  • export --with-references writes it after the code.
  • import --with-references restores the references first, then imports the code.
  • edit --with-references writes it at the start and reads it again whenever you save it. References you added to the file are added to the document, and the document is saved. Removing an entry from the file does not remove the reference; for that, use references remove or references import --sync.

If the references cannot be written or restored, export and import still transfer the code, and end with a non-zero exit code.

Up to 0.6.0a4, a failed reference only produces a warning (the exit code stays 0, also for references import), and references added during an edit session are not saved until the next code change or a save of your own. Both changed after 0.6.0a4.

In 0.6.0a4, use the references commands

Up to 0.6.0a4, export and import with --with-references only print Could not export references or Could not import references and leave the references alone. There, run references export -r FILE and references import -r FILE as separate steps. This is fixed after 0.6.0a4.

Options in depth

Headers and UserForms

Every VBA module carries a header that the VBA editor hides from you: a version line, sometimes a BEGIN … END block, and Attribute VB_… lines. For a standard module the header says little. For a class it holds settings such as VB_PredeclaredId, and for a UserForm it holds the whole link to its layout. You choose where that header goes:

OptionCode file containsHeader goes toGood for
none (default)code onlynowhereProjects with only standard modules and simple classes.
--save-headerscode onlyName.headerClean code files, with headers kept out of sight.
--in-file-headersheader + codethe same fileComplete, self-contained modules. The natural choice for Git and for bidirectional editing.

The two options exclude each other. With --in-file-headers, a class module file looks like this:

export with headers in the files, sorted into folders
PS C:\Projects\budget> excel-vba export -f Budget.xlsm --vba-directory src --in-file-headers --rubberduck-folders
PS C:\Projects\budget> Get-ChildItem src -Recurse -Name -File
PS C:\Projects\budget> Get-Content src\Domain\Invoice.cls -TotalCount 12

UserForms need one of the two

A form without its header cannot be rebuilt. If a project contains UserForms and you give no header option, export and edit stop with an error that asks you to add --in-file-headers or --save-headers.

  • Edit the .frm file for code. Leave the .frx alone: it is binary, vba-edit marks it read-only, and a damaged one breaks the form.
  • Design the form's layout in the VBA editor, then run export again so the files have it.

Access does not have UserForms; its forms are a different thing, and vba-edit handles only their code.

Changing your mind

You can switch between the modes. When vba-edit sees that the header mode differs from the last export (it reads this from vba_metadata.json), it re-exports the modules and removes .header files that are no longer needed. With a module filter, the .header files of modules outside the filter stay where they are, since their code files still need them. import does not care which mode produced the files: it finds the header wherever it is, and both modes bring a module back with the same attributes.

Rubberduck folders

The VBA editor shows modules in one flat list. The Rubberduck add-in introduced a convention to organise them: a comment at the top of a module names its folder.

'@Folder("Domain.Billing")
Option Explicit

With --rubberduck-folders, vba-edit turns that convention into real directories. Dots separate levels, so the module above is written to Domain\Billing\ inside your VBA folder. Modules without the annotation stay in the root. You do not need Rubberduck installed.

PS> excel-vba edit -f Budget.xlsm --vba-directory src --rubberduck-folders --in-file-headers
src\ ├── Domain\ │ └── Invoice.cls '@Folder("Domain") ├── Reports\ │ └── Reporting.bas '@Folder("Reports") ├── Shared\ │ └── Helpers.bas '@Folder("Shared") ├── Sheet1.cls no annotation └── ThisWorkbook.cls no annotation
  • The annotation is recognised as '@Folder("A.B") or '@Folder "A.B", in any letter case, among the comment lines at the top of the module. The name must be in quotes.
  • It works both ways: when a file sits in a subfolder, import and edit write the matching annotation into the module, replacing one that names another folder. Moving a file to another folder is how you move a module. The file itself is not rewritten; the next export brings the new annotation into it.
  • Up to 0.6.0a4, a UserForm, a new class and a class whose header changed are imported with the annotation that is in the file, not with the folder the file is in. Corrected after 0.6.0a4.
  • A UserForm's .frx travels with its .frm into the folder.
  • Use the option consistently. A folder exported with it should be imported and edited with it, because it also tells vba-edit to look into subfolders.

Module filter 0.6

--include and --exclude decide which modules a command touches. They work on edit, export and import.

PS> excel-vba import --include "mod_10*.bas" helper.cls        # only what you changed
PS> excel-vba edit --exclude "Vendor_*" LockedForm.frm         # leave these alone
PS> excel-vba export --rubberduck-folders --include "Utils/*"  # one folder

A pattern is a name or a shell-style glob (*, ?), compared without regard to case against three things: the module name (Module1), the file name (Helpers_*.cls), and the path relative to the VBA folder (Utils/*).

  • --include keeps only matching modules. --exclude drops matching modules and is applied afterwards, so it wins.
  • Both take several patterns and can be repeated. Quote patterns that contain * so the shell passes them through.
  • In an edit session the filter applies to the first export and to every later file event, deletions included. An excluded module is never touched, and neither are its files.
  • One exception up to 0.6.0a4: switching the header mode removes the .header files of excluded modules too. Do not change the header mode while a filter is set with those versions. Fixed after 0.6.0a4.
  • A UserForm's .frx follows whatever was decided for its .frm.
import two modules, export without the document modules
PS C:\Projects\budget> excel-vba import -f Budget.xlsm --vba-directory src --include "Rep*" Helpers.bas
PS C:\Projects\budget> excel-vba export -f Budget.xlsm --vba-directory modules-only --exclude "Sheet*" ThisWorkbook

In a config file the same filter is written as lists. Patterns given on the command line replace the lists from the config file; they are not added to them.

include = ["Module1", "Helpers_*.cls", "Utils/*"]
exclude = ["Vendor_*", "LockedForm.frm"]

Encoding

Two encodings are involved. The VBA editor is not Unicode-aware: it reads and writes code in the Windows code page of the system, which is cp1252 on Western European and US systems. Your files are in that same code page by default, or in an encoding you choose, and vba-edit converts between the two.

--encoding ENC -e
The encoding of the files in the VBA folder, for example utf-8. On export, code is converted from the code page into it; on import it is converted back.
--detect-encoding -d
Works the encoding out for each file: a byte order mark decides, text that is valid UTF-8 is read as UTF-8, anything else as the code page. On export, a file that already exists keeps its encoding and a new file is written in the code page. Cannot be combined with --encoding or --bidirectional.

For most projects the default is the right choice, together with an editor set to the same code page. Whichever encoding you use, use it for every command on that folder.

One limit remains whatever the files use: a character the code page cannot represent, such as Japanese text on a Western system, cannot be stored in the VBA editor. When a class module or UserForm containing one has to be imported as a whole, vba-edit stops and names the character instead of importing it damaged.

Up to 0.6.0a4, stay with the code page

Up to 0.6.0a4, --encoding does not convert. Exported code is read in the encoding you name although Office wrote it in the code page, so with utf-8 a module containing an umlaut or accent fails to export or comes out garbled. --detect-encoding detects nothing there and reads every file in the system's default encoding. Use the default encoding with those versions. Both options work as described here after 0.6.0a4.

Safety prompts

vba-edit asks before it does something you might regret, and refuses a few things outright.

export over existing files: declined, then accepted with a new header mode
PS C:\Projects\budget> excel-vba export -f Budget.xlsm --vba-directory src --save-headers
PS C:\Projects\budget> excel-vba export -f Budget.xlsm --vba-directory src --in-file-headers
Existing files
export counts the VBA files already in the folder and asks before overwriting them. The default answer is No.
Header mode change
When the header option differs from the previous export, vba-edit tells you, re-exports the modules and cleans up .header files that are no longer needed.
UserForms without headers
Never silently accepted, on export or on import. See headers.
Failed updates
If replacing a module's code fails half-way, the previous code is restored rather than leaving the module empty. A class module or UserForm that is replaced as a whole is copied first and put back if the new version cannot be imported (after 0.6.0a4).

--force-overwrite

For scripts, --force-overwrite answers the prompts for you and proceeds. It does not switch off the UserForm check.

PS> excel-vba export -f Budget.xlsm --vba-directory src --force-overwrite

Without it, a run that cannot ask (because nobody is at the keyboard) treats the question as answered with No and exports nothing.

Logs and colours

--verbose -v
Prints more detail: the options in effect, resolved paths, per-module decisions, and full error traces.
--logfile [FILE] -l
Also writes a detailed log to a file. Without a name it is vba_edit.log in the current directory. The name may contain placeholders.
--no-color --no-colour
Switches coloured output off.

In a terminal, success is shown in green, warnings in yellow, errors in red, and paths and technical terms are highlighted. Colours are left out automatically when the output is redirected or piped, and when the NO_COLOR environment variable is set.

Two-way sync

Bidirectional editing experimental 0.6

A plain edit session moves code one way, from files to Office. With --bidirectional, code you change in the VBA editor is written back to your files too. You can fix a line in the debugger, switch to your editor, and find it there.

PS> excel-vba edit -f Budget.xlsm --vba-directory src --bidirectional --in-file-headers

Experimental

This mode is new and deliberately cautious: when it is not sure which side is right, it stops and asks instead of guessing. It has been exercised with real Excel, Word, PowerPoint and Access, but it has far fewer hours behind it than the one-way mode. Use it on projects that are in version control.

How it decides

For each module, vba-edit remembers the last state in which the file and Office agreed. That remembered state is the baseline. A change is copied only when the other side still equals the baseline:

File vs. baselineOffice vs. baselineResult
changedsameFile is imported into Office
samechangedOffice code is exported to the file
changedchanged, to the same textNothing to do; new baseline
changedchanged, differentlyPaused as a conflict

Timing. A saved file reaches Office once it has been stable for two scans, about five seconds. Code edited in the VBA editor is written to the file as soon as the Office application loses focus, which is exactly the moment you switch to your editor; without that trigger it follows after the same five seconds of quiet.

both directions, then a conflict and its resolution
PS C:\Projects\budget> excel-vba edit -f Budget.xlsm --vba-directory src --bidirectional --in-file-headers
PS C:\Projects\budget> excel-vba edit -f Budget.xlsm --vba-directory src --bidirectional --in-file-headers --sync-resolve files --sync-component Reporting

In this recording the VBA-editor edits were made by a script through Office automation, and the focus change did not happen, so the first export arrived after the settling time.

What is synchronised

ComponentTwo-way?
Standard modulesYes, in all four applications
Excel workbook and worksheet code, Word ThisDocumentYes
New standard module, created on either sideYes (in Access, save a new module in Access first)
Class modules, UserFormsNo, reported as excluded at start
Access form and report codeNo
References, and changes that affect only hidden attributesNo

Excluded components are simply not part of the session. To change them, stop and use import or a one-way edit.

When it pauses

A paused module is left alone on both sides until you decide. Other modules keep syncing. A module is paused when:

  • both sides changed differently since the baseline;
  • a file was deleted, renamed or moved, or a module disappeared in Office. Nothing is ever deleted for you in this mode;
  • the header or the module type changed;
  • an import would strip procedure or member attributes;
  • at start, the file and Office differ from what the last session left, for example after reopening a document that was closed without saving.

For each pause, both versions and the baseline are saved under <vba-directory>\.vba-edit\conflicts\, and the message tells you where. Compare them with your diff tool. What clears the pause depends on why it happened.

Clearing a pause

A disagreement about the code of a module is settled by restarting the session and naming the side that is right:

PS> excel-vba edit -f Budget.xlsm --vba-directory src --bidirectional --in-file-headers --sync-resolve office --sync-component Module1

--sync-resolve office keeps the code that is in Office and writes it to the file. --sync-resolve files keeps your file and imports it. Either applies to the one component named with --sync-component; resolve several by restarting once for each. --force-overwrite does not resolve conflicts.

These two options alone do not settle a pause that is about where a module is, what it is called, or whether it exists. Those need a step of your own first:

Why it pausedWhat clears it
Both sides changed the code, or file and Office differ at startRestart with --sync-resolve office or --sync-resolve files.
A file was deleted; the module is still in OfficeTo get the file back, restart with --sync-resolve office.
A standard module was removed in Office; the file is still thereTo get the module back, restart with --sync-resolve files.
You want the module gone for goodRemove it on both sides, the module in the VBA editor and its file, then reset the session state.
A file was renamedRename it back, then reset the session state. To rename a module, rename it in the VBA editor instead: it arrives as a new file. Delete the old file, then reset the session state.
A file was moved to another folder (--rubberduck-folders)To undo: move the file back and restart with --sync-resolve office. To make the move real: set the module's '@Folder annotation in the VBA editor to the new folder, then restart with --sync-resolve office.
The '@Folder annotation was changed in the VBA editorDelete the file in the old folder, then restart with --sync-resolve office: the file is written to the new folder.
The header in the file was changedHeaders are not imported in this mode. --sync-resolve office brings the file back in line with Office.
The file changed, and the module has procedure or member attributes--sync-resolve files is refused, because the import would strip the attributes. Make the change in the VBA editor, then restart with --sync-resolve office. That overwrites the file; your edited version stays in the conflict folder.

Resetting the session state

When a module no longer exists on either side there is nothing left to resolve, but the session still remembers it and keeps reporting the pause. To start from a clean slate, stop the session, delete <vba-directory>\.vba-edit\state.json, and start again without --sync-resolve. Every module whose file and Office code are identical becomes the new baseline. A module that differs, or exists on one side only, is paused as a difference at start, and --sync-resolve settles it as described above.

Rules of the road

  • Keep the settings stable. Restart with the same encoding, header and folder options. The session state records them and refuses to continue with different ones.
  • Keep .vba-edit\. It holds the baselines and recovery snapshots. Add it to .gitignore, and do not delete it between sessions.
  • Imports save the document. In Excel, Word and PowerPoint, every import saves the whole document, including unrelated changes you made to it. In Access, the changed module is saved.
  • Exports can contain unsaved code. What you see in the VBA editor is what gets written, whether or not the document has been saved.
  • Unsaved editor buffers are invisible. vba-edit sees files, not what is typed in your editor. Work on a module on one side at a time.
  • Nothing happens in run or break mode. While a macro is running or stopped in the debugger, synchronisation waits.
  • Stopping. Ctrl+C leaves Office open. If modules are still paused or pending, the command ends with a non-zero exit code.

The mode cannot be combined with --xlwings, --with-references or --detect-encoding. In a config file it is bidirectional = true.

Performance note for large projects: between syncs, code that Excel, Word or PowerPoint report as unchanged since the last save is not read again, so the background scans stay light. This refinement landed after 0.6.0a4.

Configuration

Config files

Once a project has settled on its options, put them in a TOML file and pass it with --conf (or --config). The same file serves edit, export, import and references. The Config Generator writes it for you.

A config file that cannot be read, because it is missing or not valid TOML, stops the command before any document is touched. The message names the problem and, for a syntax error, the line.

Up to 0.6.0a4 the command prints that error and then carries on with default settings, which can mean the active document and the folder next to it. With those versions, try a new config file with a harmless command such as references list --conf FILE first. Fixed after 0.6.0a4.

a config file at work

PS C:\Projects\budget> excel-vba export --conf vba-config.toml

vba_directory and logfile may contain placeholders, in the config file and on the command line alike. file accepts one of them, {config.path}.

Paths

  • A relative file or vba_directory is taken from the directory you run the command in, not from where the config file lies. The simplest habit is to keep the config file in the project root and run commands from there.
  • To tie a path to the config file wherever you run from, start it with {config.path}: file = "{config.path}/Budget.xlsm", vba_directory = "{config.path}/src". In file this needs a version after 0.6.0a4.
  • In double-quoted TOML strings a backslash is an escape character. Write Windows paths with forward slashes, with doubled backslashes, or in single quotes: 'C:\Projects\budget'.

Command line beats config

Anything you type on the command line overrides the file for that run. That includes switching header mode, and pattern lists, which replace the ones in the file.

PS> excel-vba export --conf vba-config.toml --vba-directory build/vba   # another folder, this once
PS> excel-vba export --conf vba-config.toml --save-headers             # although the file says in_file_headers

Extra option--xlwings

Excel

ThisWorkbook and every sheet have their own module, which exports as a .cls file. Workbooks often carry many empty sheet modules; --skip-empty keeps them out of your folder.

The xlwings wrapper. vba-edit grew out of the VBA editing feature of xlwings. --xlwings (short -x) hands the command to xlwings instead, for comparison or as a fallback. xlwings must be installed. In this mode only the file, the folder and --verbose are passed on: headers, folders, filters, references and config files are features of the native mode and do not apply.

PS> excel-vba edit -f Budget.xlsm --vba-directory src --xlwings

Word

ThisDocument exports as a .cls file. Word projects often reference templates such as Normal or your own .dotm files; those appear as references, and a reference to your own template is the classic case for a shared references file.

PowerPoint

Without --file, the tool uses the presentation in the active window, so a presentation must be open in a window. If a slide show is running, the tool uses that presentation.

Access

  • The database stays open. An edit session leaves the database open in Access; close it yourself when you are done.
  • Form and report code. The code behind a form or report is a module named Form_<name> or Report_<name>. It exports as a .cls file, and import and edit update it in place 0.6. The form itself, with its controls and layout, is not exported.
  • Such modules cannot be created by an import. Create the form or report in Access and set its Has Module property first. For an ordinary module, pick a name that does not start with Form_ or Report_.
  • Saving. Access saves modules individually rather than as part of one document; vba-edit saves a module it has re-imported so that Access does not ask for a name later.
  • Trust. Access needs a trusted database rather than the Trust Center checkbox; see allow VBA access.
  • References. The references commands work with Access in versions after 0.6.0a4.

Use cases

You maintain a workbook that matters

Put it under version control

Until now, "what changed since last month?" had no answer. After this, it is one git diff.

  1. Export the code with complete headers, so the files are full modules, and commit the result as your baseline.
  2. Work with edit running. Commit when a change is done.
  3. If you also changed code in the VBA editor, run export before committing so the files have it.
PS> excel-vba export -f Budget.xlsm --vba-directory src --in-file-headers
PS> git init -b main
PS> git add src
PS> git commit -m "Baseline export of Budget.xlsm"
baseline, a day's work, and its diff
PS C:\Projects\budget> git status --short
PS C:\Projects\budget> git diff src/Helpers.bas

A sensible .gitignore for such a repository:

.vba-edit/        # state of bidirectional sessions
vba_edit.log*     # log files
~$*               # Office lock files

Do commit the .frx files of UserForms: they are binary, but the forms cannot be rebuilt without them. Whether to commit the Office file itself is your call. It is the one thing that contains everything (sheets, data, forms), but it is binary and changes on every save.

Tell Git not to convert line endings in VBA files, since the VBA editor expects Windows line endings:

*.bas  text eol=crlf working-tree-encoding=CP1252
*.cls  text eol=crlf working-tree-encoding=CP1252
*.frm  text eol=crlf working-tree-encoding=CP1252
*.frx  binary

The working-tree-encoding part is optional. It makes Git store the files as UTF-8 internally, so that diffs on hosting sites show special characters correctly.

You want help from a coding assistant

Let an AI assistant work on your macros

Assistants such as Copilot or Claude work on files. An Office document is a locked box to them; an exported folder is ordinary source code.

  1. Start an edit session in a terminal and leave it running.
  2. Open the folder in your editor and let the assistant read and change the files there.
  3. Each change it saves reaches Office within moments. Run the macro, look at the result, and tell the assistant what you saw.
PS> excel-vba edit -f Budget.xlsm --vba-directory src --in-file-headers

A few lines of context save the assistant from the common mistakes. Put something like this in the instructions file your assistant reads:

This folder holds VBA modules exported from Budget.xlsm with vba-edit.
- Files are encoded in Windows-1252 with CRLF line endings. Keep both.
- Do not edit the header at the top of a file (VERSION, BEGIN...END,
  Attribute lines) unless asked to.
- Never edit or create .frx files. Change UserForm code in the .frm only.
- Deleting a file deletes the module in the workbook. Do not delete files
  to "clean up".
- An edit session is running: saving a file updates the workbook.

For an agent that works without a live session, import is the better fit: it reports how many files were imported and exits with a non-zero code if one failed 0.6, which an agent can check before it claims success.

Several people work on the same VBA project

Share one setup across the team

Two small files in the repository make every checkout behave the same: one for vba-edit's options, one for the project's library references.

[general]
file = "Budget.xlsm"
vba_directory = "src"
in_file_headers = true
rubberduck_folders = true
with_references = true

The paths are relative, so the file works wherever the repository is cloned. Relative paths are taken from the directory a command is run in, so everyone runs the same short commands from the repository root. (To run them from any directory, anchor both paths with {config.path}.)

PS> excel-vba import --conf vba-config.toml     # after pulling: bring the workbook up to date
PS> excel-vba edit --conf vba-config.toml       # while working
PS> excel-vba references validate -f Budget.xlsm # is every library there on this machine?

With with_references switched on, the references travel in src\Budget_refs.toml and are restored on import. A new colleague no longer has to tick the right boxes under Tools › References by hand.

Your project contains code that is not yours

Edit your code, not the vendor's 0.6

Many workbooks carry third-party modules, generated code, or a form nobody dares to touch. Exclude them once and no command will export, overwrite or delete them.

[general]
file = "Budget.xlsm"
vba_directory = "src"
in_file_headers = true
exclude = ["Vendor_*", "JsonConverter", "LockedForm.frm"]

The reverse works too. To look after a handful of modules in a large project, list them with include and everything else is left out.

You have a long editing session ahead

Refactor offline, import selectively

A live session is not required. Export, close Office, work for as long as you like with search-and-replace across all modules, and push the result back when you are ready.

PS> excel-vba export -f Budget.xlsm --vba-directory src --in-file-headers
# ... edit, rename, reorganise; Office does not need to be running ...
PS> excel-vba import -f Budget.xlsm --vba-directory src

If you only touched a few modules of a large project, import just those 0.6. It is faster, and nothing else in the document is rewritten:

PS> excel-vba import -f Budget.xlsm --vba-directory src --include "mod_10*.bas" helper.cls

Check the summary line at the end. Then open the VBA editor and choose Debug › Compile: a refactoring that looks fine as text can still fail to compile.

Your application lives in an .accdb

Work on an Access database

Access projects are mostly code behind forms and reports, plus a set of standard and class modules. All of that exports to files.

PS> access-vba edit -f Orders.accdb --vba-directory src
src\ ├── Form_Customers.cls code behind the form "Customers" ├── Form_OrderEntry.cls code behind the form "OrderEntry" ├── Report_Invoice.cls code behind the report "Invoice" ├── modPricing.bas └── clsOrder.cls
  • Saving Form_OrderEntry.cls updates the form's code in place 0.6. The form's layout stays in Access, where you design it.
  • A new form needs to exist in Access, with Has Module set, before its code file can be imported.
  • Keep the database in a trusted location, and close it yourself after the session.

You want this in a script

Scripts and automation

The commands are built to run unattended on a Windows machine that has Office installed.

PS> excel-vba export -f Budget.xlsm --vba-directory src --in-file-headers --force-overwrite --no-color
PS> git diff --quiet -- src; if ($LASTEXITCODE -ne 0) { Write-Host "Workbook and repository differ" }
PS> excel-vba references validate -f Budget.xlsm; if ($LASTEXITCODE -ne 0) { throw "Broken references" }
  • --force-overwrite answers the prompts, --no-color keeps logs clean, --logfile keeps the details.
  • import exits non-zero if a file failed 0.6, and export if a module could not be written (after 0.6.0a4). references validate exits with 1 for broken references, references import if a reference could not be added (after 0.6.0a4).
  • Hosted CI runners rarely have Office, so this is for your own build machine or a scheduled task. Office automation needs a logged-in desktop session.

The export-then-diff line is a cheap way to catch the classic problem: someone changed the macro in the workbook and never told the repository.

Known limitations

  • Windows and desktop Office only. vba-edit drives Office through its Windows automation interface. Office for Mac and Office on the web are not supported.
  • Form layouts are designed in Office. The .frx of a UserForm is carried along but not editable as text, and Access forms and reports export only their code.
  • One-way edit does not notice changes in the VBA editor. Use export, or the experimental bidirectional mode.
  • Bidirectional editing covers standard and document modules only, and is experimental.
  • A .header file edited alone is not synced. Save the matching code file too.
  • Templates and add-ins (.xltm, .xlam, .dotm, .potm) are likely to work but little tested.
  • Password-protected VBA projects must be unlocked in the VBA editor before Office allows access to their code.

The stable release is 0.5.1. This guide describes 0.6.0, currently available as the pre-release 0.6.0a4. The full history is in the changelog.

New in 0.6.0

  • Bidirectional editing (experimental), with the focus-loss trigger contributed by @russ-who.
